Fleet review gate

An automated review loop between engineers and an AI agent fleet that opens pull requests, at SeamlessHR.

Running for two engineers · Read-only reviews · Nothing merges without a human tap

Designer and builder, end to end · 2026 – present

Business goal

Let the company's AI dev agents keep shipping pull requests on production HR repositories without an engineer re-reading every PR or relaying every fix by hand.

Context

  • –A fleet of AI agents opens pull requests on the recruitment and HRMS repositories, and CI posts an automated review. Turning its blockers into a fix request, checking each new push and chasing fixes that were only partly done was manual work for whoever was watching.
  • –The dev agent takes its instructions in Slack, not from Jira or PR comments, so the automation had to work through Slack in the agent's own format.
  • –No admin rights and no public URL: it had to run from an engineer's own machine.

Architecture

Decisions

Nothing exposed to the internet

Slack talks to the machine over Socket Mode, an outgoing WebSocket, so there is no webhook to host or get approved. GitHub and Jira are polled every five minutes by launchd.

Two processes with separate jobs

A poller finds fleet PRs, reads the CI verdict, queues a local review, sends fix requests and posts a weekday brief. An always-on listener handles review cards, buttons and follow-up questions, answered by resuming the Claude session that wrote that review.

Reviews can read, never write

Each review is headless Claude with read-only tools, running on a git worktree of the PR head, given domain notes for the recruitment and HRMS modules, with a cost cap per review.

Bounded autonomy

Fix requests go to the dev agent as the engineer, signed so they can be told apart from typed messages. After three rounds it hands the PR back to a person. It never merges, force-pushes or changes a ticket without a tap.

Sends are idempotent

Before sending a fix, it searches Slack for an earlier one against the same head commit, so restarts and overlapping runs don't send twice. It can only see its owner's messages, so two engineers split the work by repository or by role.

A cloud fallback that never overlaps

A GitHub Actions copy keeps the gate running while the laptop is asleep. The local engine writes a heartbeat every five minutes, and the cloud job skips while that heartbeat is under fifteen minutes old.

Result

  • –Gates the fleet's pull requests every weekday, with the agent loop running unattended between human decisions.
  • –Running for two engineers, each with their own instance. A setup guide gets a teammate running in about two hours, with no admin rights.
